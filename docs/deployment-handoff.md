## 1. Purpose and scope

Phase 1 adds monitoring only: traces and logs over OpenTelemetry, metrics over Prometheus, dashboards and alerting in Grafana.
It deploys:

- A new `luvax-observability` Coolify resource (ClickHouse, Prometheus, Grafana, the OTel Collector, a Docker socket proxy, and five Prometheus exporters).
- Backend code changes already merged to `develop` and released through the normal Coolify deploy of the `luvax-prod` application (OTLP export, a private management port, outbox/inbox metrics, `pg_stat_statements`).
- A `luvax_monitor` role on the production Postgres and a `luvax_monitor` user on the production Elasticsearch, both read-only.
- One new public hostname, `grafana.luvax.online`, behind Cloudflare Access.

It does not touch:

- The frontend.
  No frontend code, build, or deploy is part of this phase.
- Phase 2 (analytics on the same ClickHouse instance) or Phase 3 (whatever follows).
  Both are out of scope here and are not prerequisites.
- Any of the existing application resources' business logic.
  The backend changes are additive: new endpoints, new metrics, new migrations (V124-V126), no removed behavior other than the actuator endpoints leaving the public application port (see R6 and the risk list in section 5).

## 3. Current production topology

### Host constraints

- CPU: SSE4.2 only, no AVX2, no FMA.
  This is why ClickHouse is pinned (see section 9).
- 8 cores, 32 GB RAM.
- No public ports.
  The only path in is Cloudflare Tunnel `luvax-tunnel`; the only path for administration is Tailscale.
- Every resource in this document runs on this one host, under Coolify 4.3.23.

### Coolify conventions this deployment depends on

- Every resource Coolify manages carries `coolify.type`, `coolify.resourceName` and (for a compose service) `coolify.serviceName` labels.
  `docker inspect <container> --format '{{json .Config.Labels}}' | jq 'with_entries(select(.key|startswith("coolify")))'` reads them.
- A Coolify Docker Compose resource's bind mounts must point at files that already exist on the host.
  A bind mount whose source path is missing does not fail the deploy — Docker silently creates an empty **directory** at that path instead, and everything downstream that expected a file there breaks in a way that looks unrelated to the missing file (see section 9, "Coolify creating directories for missing bind-mount files").
  This is why R1 (populating `/data/luvax/observability`) must complete, and must be verified with `find /data/luvax/observability -type d -empty` printing nothing, before R5 ever deploys the compose resource.
- Two Coolify resources can resolve each other by container name only if both are attached to the same Docker network.
  Every resource in this deployment is attached to the shared external network named `coolify` (enabled per-resource with the "Connect To Predefined Network" toggle); a resource left off that network cannot be reached by name from any other resource, including by an exporter or by the collector's container-log discovery.
  This was verified directly in the local rehearsal: every container below resolved every other by its container name only after joining a common network.
- A Coolify **Application** resource (the backend) gets a stable **network alias** (`luvax-backend`) rather than a stable container name; the container name itself changes on every deploy.
  Anything that needs to reach the backend by name (Prometheus, in this case) must resolve the alias, not a container name — this is why the production Prometheus job uses `dns_sd_configs` against `luvax-backend` rather than a static target, and why a rolling deploy is expected to show two `luvax-backend` targets briefly (P1) rather than an error.

### The `api.luvax.online` tunnel origin settings, and why routing to port 80 loops

Every public hostname on `luvax-tunnel` routes through the Coolify proxy on the same host.
The existing `api.luvax.online` rule works only because it points at `https://localhost:443` with the HTTP Host Header and TLS Origin Server Name both set to `api.luvax.online`, and HTTP/2 to origin turned off.
The new `grafana.luvax.online` rule must mirror this shape exactly, with its own hostname in place of `api.luvax.online`, and it must sit before the tunnel's catch-all rule (same place every other hostname rule sits).

Routing to `http://localhost:80` instead loops: the tunnel terminates TLS and forwards a plain HTTP request to Coolify's proxy, and Coolify's proxy responds to plain HTTP with its own redirect to HTTPS on the *same public hostname* — which the browser follows back through the tunnel, which terminates TLS and forwards plain HTTP again.
Copying only the `service` field from the `api.luvax.online` rule (and not the Host Header / Origin Server Name / HTTP-2 settings) reproduces this loop, or produces a TLS name mismatch, because the proxy's TLS listener uses SNI/Host Header to choose which resource's certificate to present.

## 6. Known differences from a from-scratch reading of the runbook

These are not failure modes (section 9 covers those).
They are corrections the local rehearsal made to the runbook's own text, described here once so you do not need to reconcile two versions:

- **R1's sync script now targets this repository, not the root aggregator.**
  `scripts/sync-to-host.sh`'s default `REPO_URL` used to point at `luvax-social/Luvax.git` and rsync its `observability/` subdirectory.
  That subdirectory stopped existing there once this stack moved into its own repository: a plain `git clone` of the root aggregator does not check out submodule content, so the old default produced an empty target directory.
  The script now clones this repository directly, at its own root.
  If your checkout of this script still shows the old `Luvax.git` default, pull `main` again before running R1.
- **R3 must also create the `gorse` database.**
  Nothing else in this runbook provisions it: the backend's own dev Postgres image runs an init script that only fires on a first-boot empty volume, which the production, Coolify-managed Postgres never runs.
  Provisioning `luvax_monitor` without also running `CREATE DATABASE gorse;` leaves Gorse crash-looping on `pq: database "gorse" does not exist`, forever, with a healthy-looking Postgres right next to it.
  R7 below includes this statement in R3's SQL block; if you are working from an older copy of this runbook that does not, add it.
- **The `host-containers` dashboard's "Collector throughput and failures" panel queried the wrong metric names.**
  It queried `otelcol_exporter_sent_log_records_total`, `otelcol_exporter_sent_spans_total` and `otelcol_exporter_send_failed_log_records_total`; the collector actually exposes these counters without the `_total` suffix (confirmed by reading `otel-collector:8888/metrics` directly).
  The panel showed "No data" regardless of real traffic.
  Fixed on `main`; if this panel is ever blank again, check the exact metric names the running collector version exposes before assuming it is a traffic problem.

### R3 — Extension, monitoring role, and the Gorse database

Who: you, **[WRITE]** only on explicit request.

```bash
docker exec -i $PG psql -U postgres -d <app_db> -v ON_ERROR_STOP=1 <<'SQL'
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
CREATE ROLE luvax_monitor WITH LOGIN PASSWORD '<POSTGRES_MONITOR_PASSWORD>' CONNECTION LIMIT 5;
GRANT pg_monitor TO luvax_monitor;
GRANT CONNECT ON DATABASE <app_db> TO luvax_monitor;
SQL
docker exec $PG psql -U postgres -tAc "SELECT 1 FROM pg_database WHERE datname = 'gorse'" | grep -q 1 || \
  docker exec $PG psql -U postgres -tAc "CREATE DATABASE gorse"
```

The second command is idempotent and safe to run even if Gorse already has its database; it only creates one if missing.
If Gorse has been crash-looping on `pq: database "gorse" does not exist` in `docker logs $GORSE`, this is why, and this line fixes it — restart the Gorse container afterward if it is currently in a restart loop.

Verification:

```bash

docker exec $PG env PGPASSWORD='<POSTGRES_MONITOR_PASSWORD>' psql -U luvax_monitor -d <app_db> -h 127.0.0.1 -tAc "CREATE TABLE probe(x int)"   # permission denied
docker exec $PG psql -U postgres -tAc "SELECT datname FROM pg_database WHERE datname = 'gorse'"   # gorse
```

## 9. Known failure modes and diagnosis

- **ClickHouse `SIGILL` above 26.5 on this CPU.**
  From ClickHouse 26.6 the official build's default target is x86-64-v3 (AVX2); this host's CPU is SSE4.2 only.
  `26.8.10.6` was reproduced crashing with `SIGILL` here while `26.3.33.24` (x86-64-v2) ran.
  Never move `compose.prod.yaml`'s ClickHouse image past the 26.3 LTS line on this host.
  This constraint outlives Phase 1 — Phase 2 analytics on the same instance inherits it until the host's CPU model changes.
- **Gorse OpenBLAS `SIGILL`.**
  The same CPU constraint applies to Gorse's OpenBLAS-linked binary; `compose.prod.yaml`'s Gorse-adjacent tuning (`OPENBLAS_CORETYPE=NEHALEM`, if Gorse's own resource sets it) exists for the same reason.
  If Gorse crashes with `SIGILL` rather than the `gorse` database-missing error below, this is the cause — confirm the CPU flags again with R0's `lscpu` line.
- **Grafana crash on an empty Discord webhook.**
  Grafana's Discord contact point provisioning fails validation on a syntactically empty URL, and that failure is fatal to the whole server, not just to alerting.
  `compose.prod.yaml` sets a syntactically valid placeholder default (`GF_DISCORD_WEBHOOK_URL:-https://discord.com/api/webhooks/000000000000000000/placeholder-pending-r9}`) for exactly this reason — R5 deploys before R9 sets the real value.
  Do not remove that default while wiring the real variable at R9; only replace the value.
- **ClickHouse reader `readonly` level.**
  The Grafana ClickHouse plugin always sets `max_execution_time` per query.
  A reader profile with `readonly=1` rejects any query that sets a setting, which breaks every ClickHouse-backed panel on every dashboard, not just one.
  The reader profile in `clickhouse/users.d/luvax.xml` uses `readonly=2` (settings changes allowed, everything else still read-only) for this reason — do not "harden" it back to `1`.
- **The `okio` conflict.**
  A transitive dependency conflict blocked OTLP export at the backend level; already fixed in the merged backend PR (commit `6860c601`, verified via `mvn dependency:tree -Dincludes=com.squareup.okio` resolving to one version).
  Mentioned here only so it is recognized if it resurfaces after an unrelated dependency bump: symptom is traces/logs silently not arriving in ClickHouse with no exception in the backend's own logs, because the conflict manifests inside the exporter's own HTTP client.
- **Scrape targets down after a backend redeploy.**
  Expected and transient if using `dns_sd_configs` correctly (see R6's rolling-deploy note); a target that stays down for more than one scrape interval after the deploy finishes is a real problem — check the new container actually joined the `coolify` network and carries the `luvax-backend` alias.
- **Collector log-file permissions.**
  The OTel Collector reads `/var/lib/docker/containers/**/*.log` directly and runs as `user: "0"` in `compose.prod.yaml` specifically because those files are root-owned on the host.
  Do not remove that `user: "0"` as a hardening pass; the collector cannot read container logs without it, and the failure mode is silent (no error, just no rows for the affected containers).
- **Postgres custom configuration replacing the whole file.**
  Covered in R2 above — pasting only the four new lines instead of the full `pg_settings` dump silently reverts every other setting to the image's default.
  If Postgres behaves oddly after R2 (connection limits, timezone, locale), this is the first thing to check: `docker exec $PG psql -U postgres -tAc "SELECT name, setting FROM pg_settings WHERE source = 'configuration file' ORDER BY name"` and diff against R0's original dump.
- **Tunnel redirect loop.**
  Covered in section 3 above.
  Diagnosis: `curl -sIL --max-redirs 5 https://grafana.luvax.online` either exhausts its redirect budget or alternates `301`/`302` between the same two URLs.
  Fix is R8's exact origin settings (Host Header, Origin Server Name, HTTP/2 off), not a different `service` URL.
- **Coolify creating directories for missing bind-mount files.**
  Covered in section 3.
  If any observability service fails to start with an error about a config file being a directory, or being unreadable/empty when it should have real content, this is almost certainly it: re-run R1's verification (`find /data/luvax/observability -type d -empty`) and fix whichever path is empty, then restart that one service — no need to redeploy the whole resource.
- **Gorse crash-looping on a missing database.**
  New finding from this rehearsal, not previously documented: nothing in the original runbook provisioned the `gorse` database on the production Postgres (the backend's own dev-only init script that does this never runs against Coolify's managed Postgres).
  Symptom: `docker logs $GORSE` shows `pq: database "gorse" does not exist (3D000)` in a tight restart loop, while Postgres itself reports healthy.
  Fixed by adding the `CREATE DATABASE gorse` statement to R3 above; if Gorse is already stuck in this loop, run that one statement and restart the Gorse container.
- **The sync script cloning the wrong repository.**
  New finding from this rehearsal: `scripts/sync-to-host.sh`'s `REPO_URL` default used to point at the root aggregator (`luvax-social/Luvax.git`) and rsync its `observability/` subdirectory, a layout that stopped existing once this stack became its own repository.
  Fixed on `main`; if R1 ever produces an empty target directory again, check this script's `REPO_URL` default first.
- **A dashboard panel with a metric-name typo looks identical to a real traffic gap.**
  The `host-containers` fix above cost real investigation time precisely because "No data" on a throughput panel is the expected symptom of both causes.
  Before concluding a panel's data source has no traffic, curl the exporter or collector's own `/metrics` endpoint directly and grep for the metric name the panel queries; a name that is not there at all means the query is wrong, not the traffic.

Known differences from production, all forced by the local machine rather than by anything this repository ships:

- **Memory.**
  Docker Desktop on this machine is capped at roughly 7.6 GB total; `compose.prod.yaml`'s own limits sum to 7.3 GB and the real host has 32 GB.
  The rehearsal ran with ClickHouse's `mem_limit` lowered to 1536m in a local-only compose override (not committed anywhere) so the whole stack plus backend infrastructure would fit; `compose.prod.yaml`'s real 4096m limit was never changed and is what actually ships.
- **CPU features.**
  This rehearsal's CPU is a modern desktop/server part with AVX2 available; it cannot reproduce the `SIGILL` that motivates pinning ClickHouse and watching Gorse's OpenBLAS build.
  That constraint is proven by prior source-level and `qemu -cpu Nehalem` analysis (see `P1-observability-implementation-plan.md` section 2 in the root aggregator's checkout), not by this rehearsal.
- **`sudo` and `rsync` do not exist on this machine's shell.**
  `scripts/sync-to-host.sh` was proven correct by running it inside a disposable Debian container instead (which does have both), not directly on the Windows host.
  The real production host is Linux and has both natively.
- **`node-exporter` and `cadvisor`'s host mounts see Docker Desktop's Linux VM, not a bare-metal host.**
  This was already documented from the P1/P2 work: the `host-containers` dashboard's "Root disk used" panel legitimately shows no data locally because Docker Desktop's WSL2 VM exposes no conventional `/` mountpoint, while the same PromQL is correct on a real Linux host.
- **No Cloudflare or Coolify access from this machine.**
  R7, R8's actual dashboard/API steps, and R9's real webhook delivery were not exercised.
  R8's origin-configuration behavior was rehearsed indirectly (see above) and R9's Discord delivery was not verified (no Discord webhook was available to this session; the alert firing and resolving in Grafana's own alert state was verified, only the outbound message was not).
- **Most panels carried only a handful of synthetic requests, not sustained traffic.**
  A handful of manual API calls and three text posts are enough to prove every pipeline wired correctly (traces, logs, metrics all showed real values on inspection), but several rate()-based panels (outbox publish rate, inbox outcomes, JVM request rate) legitimately read "No data" or a near-invisible flat line at the exact moment of the screenshot sweep, the same class of artifact P2's rehearsal already documented for the `jvm-http` "Slowest routes" panel.
  This is expected under sustained production traffic and is not something to chase further; the underlying meters were confirmed correct by reading `/actuator/prometheus` and the collector's own `/metrics` directly wherever a panel looked suspicious.
- **The Windows checkout building the rehearsal's backend image needed a workaround, not a fix.**
  `docker build` against this Windows checkout's working tree failed Spotless because `core.autocrlf=true` converts the repository's LF-committed source to CRLF on checkout; even `git archive` reproduces this on Windows unless invoked as `git -c core.autocrlf=false archive HEAD`.
  This is a Windows-only artifact of building the image locally: the real host is Linux and Coolify's own build never touches a Windows checkout, so nothing in the shipped repository needed to change.
